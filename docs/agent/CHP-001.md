# CHP-001 — Capability Harvest Protocol

**Authority:** Gavin, 2026-11-14. He gave the protocol, then wrote: "Capability Harvest 001 is accepted as our
research baseline", with three standing improvements, which are recorded below.
**What it is:** a working approach for continuous product advancement. **What it is not:** it changes no workflow
rule. DEV-FLOW-002 still governs branches, review, risk lanes and merges, and AGENTS.md's leverage gate still applies
to every brief and PR. It grants no implementation authority: each build mission still needs Gavin's approval.

*Operating principle: discover what works, identify what is missing, build what matters.*

## Stages

1. **Discover.** Research excellent commercial apps and open-source projects relevant to one BEYOND subsystem. Find
   what each does exceptionally well.
2. **Inspect.** Examine BEYOND's actual repository and behaviour, then decide whether each capability exists, how
   well it works, and whether the reference is meaningfully better.
   - **Standing improvement 1:** inspect the locked product and design decisions alongside the code
     (`docs/UX_DECISIONS.md`, `docs/OPERATOR_INTERFACE_DOCTRINE.md`). A capability can exist in code and still be
     constrained by a locked decision, such as POLISH-002's faces or the emblem's places.
3. **Classify** each opportunity:
   - **EXISTING**: implemented adequately;
   - **REFINE**: implemented, but meaningfully improvable;
   - **MISSING**: valuable and not implemented;
   - **REJECT**: unsuitable, redundant or against doctrine.

   "Exists" means interaction parity, not just a matching name (for example, Harvest 001's lifestyle-logging
   follow-up).
4. **Rank** against daily usefulness, effort, integration value, reliability and maintenance risk, visual and
   interaction quality, and doctrine fit. Prefer what makes existing systems more useful and better connected.
5. **Build.** Turn the highest-value *approved* opportunity into a bounded mission under DEV-FLOW-002. Preserve
   architecture, data, workflows and identity unless a change is explicitly authorised.
6. **Verify.** Use the right automated tests, independent review where DEV-FLOW-002 requires it, and Gavin's
   explicit merge approval. Record what changed and name the next opportunity.

## Standing rules

- Improve before duplicating. Adapt excellent ideas; never copy an app blindly.
- **Standing improvement 2:** record each reference's licence in the harvest before considering any external code
  reuse.
  - **GPL and AGPL** (for example Loop, Gadgetbridge, wger code): ideas only.
  - **MIT and Apache:** may be adapted with attribution.
  - **Data under Creative Commons:** only with its stated attribution.
  - **Proprietary products:** ideas only, never their assets or identity.
- Preserve local-first ownership, the deterministic Engine's authority, and "Alfred proposes, the operator
  confirms".
- Keep the Batman Beyond identity while refining it.
- No guilt, manufactured urgency or needless complexity. The operator approves.
- **Standing improvement 3:** save every completed harvest in the repository as
  `docs/agent/harvest/HARVEST-NNN.md`, indexed from `docs/agent/CAPABILITY_MAP.md`, so research is reused and not
  repeated. In each harvest, separate verified findings from recommendations and from unresolved questions.
